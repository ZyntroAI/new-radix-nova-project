# สถาปัตยกรรมระบบเตือนความจำสำหรับ Agent หลายภูมิภาค

## 1. ภาพรวม

ระบบเตือนความจำช่วยให้เอเจนต์บันทึก ติดตาม และส่งการแจ้งเตือนตามเวลา โดยทำงานร่วมกันได้ระหว่างหลายภูมิภาค ระบบต้องคำนึงถึงเขตเวลา ความพร้อมใช้งาน ความเป็นส่วนตัว และการส่งซ้ำอย่างปลอดภัย

องค์ประกอบหลัก:

- **Agent:** รับคำขอ สร้างหรือจัดการการเตือน และตอบกลับผู้ใช้
- **AgentTools:** เครื่องมือสำหรับสร้าง แก้ไข ยกเลิก และค้นหาการเตือน
- **AgentSandbox:** สภาพแวดล้อมทดสอบพฤติกรรมและเหตุการณ์จำลอง
- **Agent-Validator:** ตรวจสอบคำขอ กฎธุรกิจ และผลลัพธ์ก่อนดำเนินการ
- **Reminder API:** จุดรับคำสั่งและส่งข้อมูลระหว่างบริการ
- **Reminder Store:** จัดเก็บการเตือนและสถานะอย่างถาวร
- **Scheduler:** ค้นหาการเตือนที่ถึงกำหนดและสร้างงานส่งแจ้งเตือน
- **Delivery Workers:** ส่งการแจ้งเตือนผ่านช่องทางที่กำหนด
- **Regional Router:** เลือกภูมิภาคสำหรับประมวลผลและส่งงาน

## 2. เป้าหมายและข้อกำหนด

### เป้าหมาย

- สร้าง แก้ไข ดู และยกเลิกการเตือนได้
- รองรับการเตือนครั้งเดียวและการเตือนแบบเกิดซ้ำ
- รองรับผู้ใช้และเอเจนต์ในหลายภูมิภาค
- ส่งการแจ้งเตือนตามเวลาท้องถิ่นที่ผู้ใช้ตั้งใจ
- ป้องกันการส่งซ้ำจากการลองใหม่หรือระบบขัดข้อง
- ตรวจสอบย้อนหลังได้ว่าเกิดอะไรขึ้นกับการเตือนแต่ละรายการ

### ข้อกำหนดที่ไม่ใช่เป้าหมาย

- ไม่รับประกันว่าการแจ้งเตือนจะปรากฏบนอุปกรณ์ทันที หากช่องทางปลายทางหรือเครือข่ายขัดข้อง
- ไม่ใช้เขตเวลาของเซิร์ฟเวอร์เป็นตัวแทนเขตเวลาของผู้ใช้
- ไม่อนุมานเวลาหรือวันที่คลุมเครือโดยไม่ยืนยันกับผู้ใช้

## 3. สถาปัตยกรรมระดับสูง

```text
ผู้ใช้
  │
  ▼
Agent
  │ เรียกใช้ AgentTools
  ▼
Reminder API ───────► Agent-Validator
  │                       │
  │                       └─ ตรวจข้อมูลและนโยบาย
  ▼
Reminder Store
  │
  ▼
Regional Router
  │
  ▼
Scheduler ──► งานส่งแจ้งเตือน ──► Delivery Workers
                                      │
                                      ▼
                              Push / อีเมล / ข้อความ
```

AgentSandbox ใช้ทดสอบคำขอ การเลื่อนเวลา การส่งซ้ำ และเหตุการณ์ขัดข้องโดยไม่ส่งการแจ้งเตือนจริง

## 4. แบบจำลองข้อมูล

ตัวอย่างโครงสร้างการเตือน:

```json
{
  "reminder_id": "rem_01J...",
  "user_id": "usr_123",
  "agent_id": "agt_456",
  "title": "ประชุมทีม",
  "message": "เตรียมสรุปงานก่อนประชุม",
  "schedule": {
    "kind": "once",
    "local_datetime": "2026-10-12T09:00:00",
    "timezone": "Asia/Bangkok",
    "due_at_utc": "2026-10-12T02:00:00Z"
  },
  "region": "ap-southeast",
  "channel": "push",
  "status": "scheduled",
  "created_at": "2026-10-02T06:00:00Z",
  "updated_at": "2026-10-02T06:00:00Z",
  "version": 1
}
```

### ฟิลด์สำคัญ

- `reminder_id`: รหัสเฉพาะของการเตือน
- `user_id`: เจ้าของการเตือน
- `schedule.timezone`: เขตเวลาที่ใช้ตีความเวลาท้องถิ่น
- `schedule.due_at_utc`: เวลาที่ใช้จัดเรียงและประมวลผลในระบบ
- `region`: ภูมิภาคที่รับผิดชอบข้อมูลหรือการส่งงาน
- `status`: สถานะปัจจุบัน
- `version`: ใช้ควบคุมการแก้ไขพร้อมกัน

ควรเก็บทั้งเวลาท้องถิ่นและเวลา UTC เพื่อรักษาความตั้งใจเดิมของผู้ใช้และให้ Scheduler ประมวลผลได้สม่ำเสมอ

## 5. สถานะและวงจรชีวิต

สถานะที่แนะนำ:

```text
draft → scheduled → processing → delivered
                    │             └→ failed
                    ├→ cancelled
                    └→ scheduled (เมื่อเลื่อนหรือ retry)
```

- `draft`: ยังตรวจสอบหรือยืนยันข้อมูลไม่เสร็จ
- `scheduled`: รอถึงกำหนด
- `processing`: มี Worker รับงานแล้ว
- `delivered`: ช่องทางปลายทางตอบรับการส่ง
- `failed`: ส่งไม่สำเร็จหลังลองใหม่ครบจำนวน
- `cancelled`: ผู้ใช้หรือเอเจนต์ยกเลิกแล้ว

คำว่า `delivered` หมายถึงช่องทางปลายทางยืนยันการรับงาน ไม่จำเป็นต้องหมายความว่าผู้ใช้เห็นการแจ้งเตือนแล้ว

## 6. การจัดการเวลาและเขตเวลา

1. รับเวลาท้องถิ่นพร้อมเขตเวลาที่ระบุชัดเจน เช่น `Asia/Bangkok`
2. แปลงเป็น UTC เพื่อใช้จัดคิว
3. เก็บค่าเวลาท้องถิ่นและเขตเวลาเดิมไว้ด้วย
4. สำหรับการเตือนที่เกิดซ้ำ ให้คำนวณครั้งถัดไปจากกฎเวลาท้องถิ่น ไม่ใช่บวกช่วงเวลา UTC แบบตายตัว
5. หากเวลาไม่มีอยู่หรือซ้ำกันจากการเปลี่ยนเวลาออมแสง ให้ใช้กฎที่กำหนดไว้ล่วงหน้า หรือขอให้ผู้ใช้ระบุเวลาใหม่
6. หากผู้ใช้ย้ายภูมิภาค อย่าเปลี่ยนเขตเวลาของการเตือนเดิมโดยอัตโนมัติ ควรให้ผู้ใช้เลือกว่าจะคงเวลาเดิมหรือปรับตามเขตเวลาใหม่

คำขออย่าง “เตือนพรุ่งนี้เช้า” ควรถูกแปลงเป็นวัน เวลา และเขตเวลาที่แน่นอน หากข้อมูลยังคลุมเครือ Agent ควรถามยืนยันก่อนสร้างรายการ

## 7. การเกิดซ้ำ

รองรับกฎเกิดซ้ำในรูปแบบที่ตรวจสอบและตีความได้ เช่น:

```json
{
  "kind": "recurring",
  "rule": "FREQ=WEEKLY;BYDAY=MO,WE,FR",
  "local_time": "09:00:00",
  "timezone": "Asia/Bangkok",
  "end_at": null
}
```

แนวทาง:

- เก็บกฎเกิดซ้ำและเวลาท้องถิ่นเป็นข้อมูลต้นฉบับ
- สร้างรายการครั้งถัดไปล่วงหน้าใน Scheduler
- เมื่อแก้กฎ ให้ยกเลิกงานที่ยังไม่ส่งซึ่งสร้างจากกฎรุ่นเก่า
- กำหนดพฤติกรรมเมื่อเวลาที่กำหนดผ่านไปแล้ว เช่น ข้ามรอบนั้นหรือส่งทันที โดยให้สอดคล้องกับผลิตภัณฑ์

## 8. บทบาทของ Agent และเครื่องมือ

### Agent

- แปลคำขอของผู้ใช้ให้เป็นข้อมูลเตือน
- ถามยืนยันเมื่อวันที่ เวลา หรือเขตเวลาไม่ชัดเจน
- สรุปผลการสร้างหรือแก้ไขให้ผู้ใช้เข้าใจง่าย

### AgentTools

เครื่องมือที่แนะนำ:

- `create_reminder`
- `get_reminder`
- `list_reminders`
- `update_reminder`
- `cancel_reminder`
- `snooze_reminder`

ทุกคำสั่งเปลี่ยนแปลงควรมี `idempotency_key` เพื่อป้องกันการสร้างหรือแก้ไขซ้ำเมื่อคำขอถูกส่งใหม่

### Agent-Validator

ตรวจสอบอย่างน้อยเรื่องต่อไปนี้:

- ผู้ใช้มีสิทธิ์จัดการการเตือนนั้นหรือไม่
- วันที่และเวลาเป็นค่าที่ถูกต้องหรือไม่
- เขตเวลามีรูปแบบที่รองรับหรือไม่
- กฎเกิดซ้ำถูกต้องและมีขอบเขตหรือไม่
- เนื้อหาการเตือนไม่ละเมิดนโยบายหรือข้อจำกัดของช่องทาง
- การแก้ไขไม่ทำให้เกิดสถานะขัดแย้ง

### AgentSandbox

ใช้จำลองกรณี เช่น:

- สร้างและยกเลิกการเตือน
- คำขอซ้ำที่มี idempotency key เดิม
- Worker ทำงานล้มเหลวแล้วลองใหม่
- Scheduler ทำงานช้าหรือทำงานซ้ำ
- การเปลี่ยนเขตเวลาและเวลาออมแสง
- ภูมิภาคหลักใช้งานไม่ได้และต้องส่งต่องาน

## 9. API ที่แนะนำ

### สร้างการเตือน

```http
POST /v1/reminders
Idempotency-Key: 8d1...
```

```json
{
  "title": "ประชุมทีม",
  "message": "เตรียมสรุปงาน",
  "local_datetime": "2026-10-12T09:00:00",
  "timezone": "Asia/Bangkok",
  "channel": "push"
}
```

### อ่านการเตือน

```http
GET /v1/reminders/{reminder_id}
```

### รายการการเตือน

```http
GET /v1/reminders?status=scheduled&limit=50
```

### แก้ไขการเตือน

```http
PATCH /v1/reminders/{reminder_id}
If-Match: 3
```

ใช้ `If-Match` หรือหมายเลขเวอร์ชันเพื่อป้องกันการเขียนทับการเปลี่ยนแปลงของคำขออื่น

### ยกเลิกการเตือน

```http
POST /v1/reminders/{reminder_id}/cancel
```

## 10. การจัดคิวและการส่ง

1. Scheduler เลือกรายการที่ถึงกำหนดด้วยดัชนีตาม `due_at_utc` และ `status`
2. ทำเครื่องหมายหรือจองรายการแบบอะตอมมิก เพื่อไม่ให้ Worker หลายตัวประมวลผลรายการเดียวกันพร้อมกัน
3. สร้างงานส่งที่มี `reminder_id` และ `delivery_attempt`
4. Worker ตรวจสอบว่ายังไม่ถูกยกเลิกหรือแทนที่ด้วยเวอร์ชันใหม่
5. ส่งผ่านช่องทางที่กำหนด
6. บันทึกผลและอัปเดตสถานะ
7. หากล้มเหลวชั่วคราว ให้ลองใหม่ด้วย exponential backoff พร้อม jitter
8. หากเกินจำนวนครั้งที่กำหนด ให้ส่งเข้าคิวตรวจสอบหรือทำเครื่องหมาย `failed`

เพื่อป้องกันผลกระทบจากการส่งซ้ำ ให้ใช้คีย์เฉพาะของงาน เช่น:

```text
delivery:{reminder_id}:{scheduled_occurrence}
```

การส่งแบบ exactly-once ข้ามระบบภายนอกมักรับประกันได้ยาก ควรออกแบบให้ส่งซ้ำได้อย่างปลอดภัยและตรวจจับการทำงานซ้ำ

## 11. การทำงานหลายภูมิภาค

### การเลือกภูมิภาค

กำหนดภูมิภาคจากข้อกำหนดด้านถิ่นที่อยู่ของข้อมูล ความหน่วง และนโยบายของผู้ใช้ อย่าเลือกจากตำแหน่งเครือข่ายเพียงอย่างเดียวหากยังไม่ได้รับอนุญาต

### การแบ่งหน้าที่

- ภูมิภาคเจ้าของข้อมูลเป็นผู้รับผิดชอบบันทึกการเตือน
- Scheduler ในภูมิภาคเดียวกันหรือภูมิภาคที่ได้รับมอบหมายสร้างงานส่ง
- Worker ส่งผ่านผู้ให้บริการที่เหมาะกับพื้นที่
- Regional Router ส่งต่องานเมื่อภูมิภาคหลักมีปัญหา ตามนโยบายข้อมูล

### ความสอดคล้อง

- ใช้การเขียนแบบมีเจ้าของหลักต่อรายการเพื่อลดการแก้ไขชนกัน
- ใช้หมายเลขเวอร์ชันและ idempotency key ระหว่างการส่งต่องาน
- ป้องกัน Scheduler สองภูมิภาคสร้างการส่งสำหรับรอบเดียวกัน
- บันทึกการเปลี่ยนภูมิภาคและเหตุผลไว้ตรวจสอบย้อนหลัง

## 12. ความปลอดภัยและความเป็นส่วนตัว

- ยืนยันตัวตนและตรวจสิทธิ์ทุกคำขอ
- จำกัดการเข้าถึงการเตือนตาม `user_id` และขอบเขตของเอเจนต์
- เข้ารหัสข้อมูลระหว่างส่งและขณะจัดเก็บ
- เก็บเฉพาะข้อมูลที่จำเป็นต่อการแจ้งเตือน
- ปกปิดเนื้อหาที่อ่อนไหวใน log และ telemetry
- รองรับการลบข้อมูลและอายุการเก็บรักษาตามนโยบาย
- ใช้ secret manager สำหรับกุญแจและข้อมูลรับรองของผู้ให้บริการ
- แยกข้อมูลทดสอบออกจากข้อมูลจริงอย่างชัดเจน

## 13. การสังเกตการณ์และการแจ้งเตือนระบบ

ตัวชี้วัดที่ควรติดตาม:

- จำนวนการเตือนที่สร้าง แก้ไข ยกเลิก และส่งสำเร็จ
- ความล่าช้าระหว่างเวลาที่กำหนดกับเวลาที่ส่ง
- อัตราความล้มเหลวและจำนวนครั้งที่ลองใหม่
- ความลึกและอายุของคิวในแต่ละภูมิภาค
- จำนวนรายการที่ถูกประมวลผลซ้ำ
- ความพร้อมใช้งานของผู้ให้บริการแจ้งเตือน

log และ trace ควรเชื่อมโยงด้วย `reminder_id`, `region`, `delivery_attempt` และรหัสติดตาม โดยหลีกเลี่ยงการบันทึกข้อความส่วนตัวเกินจำเป็น

## 14. กรณีทดสอบสำคัญ

- เวลาท้องถิ่นถูกแปลงเป็น UTC ถูกต้อง
- เวลาคลุมเครือต้องมีการยืนยัน
- การแก้ไขหรือยกเลิกก่อนเวลาส่งป้องกันการแจ้งเตือนได้
- คำขอซ้ำไม่สร้างรายการซ้ำ
- Worker ล้มเหลวแล้วลองใหม่ได้โดยไม่ส่งซ้ำโดยไม่จำเป็น
- กฎเกิดซ้ำยังรักษาเวลาท้องถิ่นเมื่อมีการเปลี่ยนเขตเวลา
- การส่งต่องานระหว่างภูมิภาคไม่ทำให้เกิดการส่งสองครั้ง
- ข้อมูลของผู้ใช้คนหนึ่งไม่สามารถเข้าถึงได้จากอีกคน
- ปลายทางไม่พร้อมใช้งานแล้วระบบบันทึกและรายงานสถานะถูกต้อง

## 15. ลำดับการพัฒนา

1. สร้าง API และแบบจำลองข้อมูลสำหรับการเตือนครั้งเดียว
2. เพิ่ม AgentTools และ Agent-Validator
3. เพิ่ม Scheduler คิวงาน และ Worker สำหรับช่องทางหนึ่ง
4. เพิ่มการลองใหม่ idempotency และ audit log
5. เพิ่มการเตือนแบบเกิดซ้ำและการจัดการเขตเวลา
6. ทดสอบด้วย AgentSandbox และจำลองความล้มเหลว
7. เพิ่มการทำงานหลายภูมิภาค พร้อมนโยบายถิ่นที่อยู่ของข้อมูล
8. เพิ่มแดชบอร์ด ตัวชี้วัด และการแจ้งเตือนผู้ดูแล

## 16. เกณฑ์ความพร้อมก่อนใช้งานจริง

- การสร้างและยกเลิกมีผลอย่างสม่ำเสมอ
- คำขอซ้ำไม่ก่อให้เกิดรายการหรือการส่งซ้ำโดยไม่ตั้งใจ
- มีนโยบายชัดเจนสำหรับเวลา เขตเวลา และการเกิดซ้ำ
- มีการจำกัดสิทธิ์และตรวจสอบย้อนหลังได้
- มีการทดสอบการส่งต่องานและความล้มเหลวรายภูมิภาค
- มีตัวชี้วัดสำหรับความล่าช้า ความล้มเหลว และคิวค้าง
- ผู้ใช้สามารถดู แก้ไข และยกเลิกการเตือนได้อย่างชัดเจน
