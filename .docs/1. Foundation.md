model

**Agent model** คือ “สมอง” ของระบบ Agent—โดยทั่วไปเป็น LLM/foundation model ที่ตีความคำขอ วางแผน เลือก Skill หรือ tool ประเมินผลลัพธ์ระหว่างทาง และตัดสินใจขั้นต่อไป แต่ model เพียงอย่างเดียวไม่ใช่ Agent ที่สมบูรณ์; Agent ต้องมี orchestration, tools, memory และ guardrails ประกอบด้วย[1][2]

## Model อยู่ตรงไหนใน Agent

```text
ผู้ใช้ / Event
      ↓
Input validation + policy
      ↓
Agent runtime / orchestrator
      ↓
Model (reasoning and decision engine)
      ↓
เลือก: ตอบ | ใช้ Skill | เรียก Tool | ส่งต่อ Agent อื่น
      ↓
Tool result / retrieved context / memory
      ↓
Model ประเมินผลและทำงานต่อ
      ↓
Output validation + approval + audit
```

Model รับผิดชอบงานเชิงความเข้าใจภาษาและการตัดสินใจ เช่น:

- จำแนกเจตนาของผู้ใช้
- เลือก Skill จาก `name` และ `description`
- แตกงานซับซ้อนเป็นขั้นตอน
- เลือก tool ที่เหมาะสมและสร้าง structured arguments
- สังเคราะห์ข้อมูลจากหลายแหล่ง
- ตรวจความครบถ้วนของผลลัพธ์
- ตัดสินใจว่าต้องถามเพิ่ม, retry, escalate หรือจบงาน

สถาปัตยกรรม Agent ที่ใช้งานจริงมักประกอบด้วย model สำหรับ reasoning, memory/retrieval, tool routing, planner/orchestrator และ verifier/guardrail ที่ตรวจ action ก่อนเกิดผลกระทบภายนอก[1][3][4]

## Model ไม่ใช่ Agent ทั้งหมด

| ชั้นระบบ           | หน้าที่                                       | ตัวอย่าง                                  |
| ------------------ | --------------------------------------------- | ----------------------------------------- |
| Model              | เข้าใจ ตัดสินใจ วางแผน และสร้างคำตอบ          | LLM ที่ตีความ “สรุป KPI เดือนนี้”         |
| Instructions       | กำหนดพฤติกรรมและข้อจำกัด                      | system prompt, `AGENTS.md`, `SKILL.md`    |
| Orchestrator       | ควบคุมลำดับงาน, retry, timeout, budget, state | agent loop และ routing policy             |
| Skills             | Workflow เฉพาะงานที่โหลดเมื่อเกี่ยวข้อง       | `monthly-reporting/SKILL.md`              |
| Tools              | ทำ action หรือดึงข้อเท็จจริง                  | database query, script, CRM API, search   |
| Memory / Retrieval | ดึงบริบทและความรู้ที่จำเป็น                   | session context, RAG, user preference     |
| Guardrails         | จำกัด ตรวจ และอนุมัติ action                  | schema validation, policy, human approval |
| Observability      | trace, audit, cost และ debugging              | tool-call logs, token/latency metrics     |

การแยกชั้นเช่นนี้สำคัญเพราะ model มีความน่าจะเป็นและอาจตัดสินใจผิดได้ ส่วนงานที่ต้อง deterministic, มีสิทธิ์สูง หรือมีผลภายนอกควรควบคุมด้วย script, schema, permission และ approval gate ไม่ใช่เชื่อ instruction ใน prompt อย่างเดียว[1][4][5]

## เกณฑ์เลือก Model

เลือก model ตาม **งานและความเสี่ยง** ไม่ใช่เลือกตัวที่ใหญ่ที่สุดเสมอไป

| Workload | ความสามารถที่ควรเน้น | แนวทาง |
|---|---|---|
| Intent routing / Skill selection | classification, multilingual understanding, structured output | ใช้ model เร็วและประหยัด พร้อม eval precision/recall |
| สรุปเอกสารและ RAG | long-context, citation discipline, instruction following | จำกัด context และบังคับ source attribution |
| วิเคราะห์หลายขั้นตอน | reasoning, planning, tool use, error recovery | ใช้ model ที่มี tool-calling reliability ดี |
| Coding / repository agent | code understanding, shell/tool discipline, test interpretation | ใช้ model ที่ทำงานกับ code และ agent loop ได้ดี |
| งานมีผลกระทบสูง | reliability, safety, auditability, controlled tool use | ใช้ model ที่ผ่าน eval เฉพาะโดเมน พร้อม approval gate |
| งานจำนวนมาก/ต้นทุนอ่อนไหว | low latency, predictable cost, batching | ใช้ model ขนาดเล็กหรือ routing แบบหลายระดับ |

อย่าดูเพียง benchmark ทั่วไป ให้ประเมินบน workload ขององค์กร เช่น trigger eval ของ Skill, tool-call schema validity, task success rate, false-positive rate, latency, token usage และอัตรา escalation[1][2][4]

## รูปแบบการใช้ Model

### 1. Single-model Agent

Model เดียวทำ routing, planning, tool use และ response

```text
User → One model → Tools/Skills → Response
```

เหมาะกับ prototype หรือ workflow ไม่ซับซ้อน ข้อดีคือดูแลง่าย แต่ควรจำกัด permissions และมี validation รอบ tool call

### 2. Model Routing

ใช้ model เล็กกับงานง่าย และส่งงานยากไป model ที่เก่งกว่า

```text
User
  ↓
Fast router model
  ├── simple request → fast/low-cost model
  └── complex or high-risk → stronger reasoning model
```

เหมาะกับองค์กรที่ต้องควบคุมต้นทุนและ latency โดยต้องมี eval วัดว่า router ส่งงานถูก tier

### 3. Specialist Models / Agents

ใช้ Agent หรือ model profile แยกตามโดเมน

```text
Coordinator
 ├── Reporting specialist
 ├── Code specialist
 ├── Legal-intake specialist
 └── Customer-support specialist
```

เหมาะเมื่อ domain มี terminology, tools, policy และ quality metric ต่างกัน แต่ต้องวาง ownership และ handoff contract ให้ชัด มิฉะนั้น complexity จะเพิ่มโดยไม่จำเป็น

### 4. Deterministic Workflow + Model

ให้ model ตัดสินใจเฉพาะส่วนที่ต้องใช้ภาษา/บริบท ส่วนขั้นตอนสำคัญทำด้วย code

```text
Model → เลือก workflow
      → Script ตรวจ schema
      → API ดึงข้อมูลที่อนุญาต
      → Script คำนวณ KPI
      → Model เขียนสรุป
      → Validator ตรวจ output
```

รูปแบบนี้เหมาะกับรายงาน การเงิน การจัดการข้อมูล หรือ compliance เพราะลดความเสี่ยงที่ model จะคำนวณผิดหรือสร้างข้อมูลขึ้นเอง

## Model Contract ที่แนะนำ

กำหนด contract ระหว่าง model กับ runtime ด้วย structured output แทนการให้ model ส่งข้อความอิสระทุกจุด

```json
{
  "decision": "use_skill",
  "skill_name": "monthly-reporting",
  "confidence": 0.91,
  "reason_code": "monthly-kpi-executive-summary",
  "required_resources": [
    "references/metric-definitions.md",
    "assets/executive-summary-template.md"
  ],
  "requires_approval": false
}
```

Runtime ต้อง validate ก่อนทำ action:

- `decision` อยู่ใน enum ที่อนุญาต
- `skill_name` เป็น Skill ที่ติดตั้งและอนุญาตจริง
- `required_resources` อยู่ใน path ที่อนุญาต
- tool arguments ผ่าน JSON Schema
- action ที่เป็น external write ต้องผ่าน approval gate โดยไม่ขึ้นกับค่า `confidence`
- model output ที่ผิด schema ต้อง retry, fallback หรือ escalate

Typed tool schemas และ verifier/critic ช่วยลดผลกระทบจากการตัดสินใจผิดหรือ output ที่ไม่เป็นรูปแบบ[1][2]

## ควบคุมต้นทุนและคุณภาพ

- โหลดเฉพาะ `name` และ `description` ของ Skills ก่อน แล้วโหลด `SKILL.md` ของ Skill ที่ถูกเลือก
- แยก `references/` และ `assets/` เพื่อให้เปิดเฉพาะเมื่อจำเป็น
- สรุป/กรอง raw data ก่อนส่งเข้า context
- ให้ scripts ทำ calculation, validation และ transform ที่ต้อง deterministic
- cache ผลการดึงข้อมูลหรือ retrieval ที่ใช้ซ้ำเมื่อ policy อนุญาต
- จำกัด tool retry, loop count, context length, token budget และเวลา execution
- log model selection, Skill selection, tool calls, schema failures, latency และ token usage
- ทำ eval แยกตามภาษา, risk tier, user group และประเภทงาน

ระบบ production ควรมี sandbox สำหรับ tool execution, schema validation, identity/permission enforcement, audit logs, caching และ observability เพื่อให้ตรวจสอบคุณภาพ ความปลอดภัย และต้นทุนได้[1][4]

## แนวทางสำหรับ Agent Skills

สำหรับโครงการ Agent Skills ที่คุณกำลังออกแบบ แนะนำ policy แบบนี้:

```text
Tier 1: Router model
- อ่านเฉพาะ Skill catalog: name + description
- ทำ task classification และเลือก/ไม่เลือก Skill
- วัด precision, recall และ false-positive rate

Tier 2: Worker model
- โหลด SKILL.md เฉพาะ Skill ที่เลือก
- ดำเนิน workflow และเรียก tool ตามสิทธิ์
- เปิด references/assets แบบ on-demand

Tier 3: Verifier
- ตรวจ schema, completeness, policy และ output constraints
- ใช้ deterministic validator ก่อนใช้ model critic
- ปฏิเสธหรือ escalate เมื่อมีความเสี่ยงสูง
```

รูปแบบนี้ใช้ model ที่เร็วและต้นทุนต่ำกับการ routing จำนวนมาก ขณะเดียวกันสงวน reasoning ที่หนักกว่าไว้สำหรับงานที่ต้องใช้จริง และทำให้ Agent Skills รองรับ Progressive Disclosure ได้อย่างมีประสิทธิภาพ[3][4]

AGENTS THINKING

**Agents Thinking** คือกลไกการตัดสินใจของ Agent ตั้งแต่ทำความเข้าใจเป้าหมาย วางแผน เลือก Skill/Tool ลงมือทำ สังเกตผล และปรับแผนจนงานเสร็จ ไม่ใช่เพียงการให้โมเดล “คิดยาวขึ้น” แต่เป็นการออกแบบวงจร reasoning ที่ตรวจสอบและควบคุมได้[1][2]

## วงจรการคิดของ Agent

รูปแบบพื้นฐานที่ใช้งานจริงคือ **Perceive → Plan → Act → Observe → Verify**

```text
User request / event
        ↓
Perceive
- เข้าใจ intent, context, constraints, risk
        ↓
Plan
- แตกงาน, เลือก Skill/Tool, กำหนด success criteria
        ↓
Act
- เรียก tool, รัน script, retrieve knowledge, สร้าง artifact
        ↓
Observe
- อ่านผล tool, error, state, evidence
        ↓
Verify
- ตรวจ schema, policy, completeness, quality
        ↓
Complete | Retry | Replan | Escalate
```

แนวคิด ReAct อธิบาย loop นี้เป็น Reason → Act → Observe → repeat: Agent เหตุผลจากสถานะปัจจุบัน เรียกใช้ tool แล้วนำ observation กลับมาปรับการตัดสินใจรอบถัดไป[3][4]

## รูปแบบการคิดที่ควรเลือกใช้

| รูปแบบ | เหมาะกับ | ข้อดี | ข้อควรระวัง |
|---|---|---|---|
| Reactive | งานง่าย คำตอบสั้น ไม่มี tool | เร็วและต้นทุนต่ำ | ไม่เหมาะกับงานหลายขั้นตอน |
| ReAct | ค้นข้อมูล วิเคราะห์ และใช้ tools หลายรอบ | ปรับตามผล tool ได้ | ต้องจำกัด loop/retry |
| Plan-and-Execute | งานซับซ้อนที่มี dependency | แผนชัด แยก planner/executor ได้ | แผนอาจล้าสมัย ต้อง replan |
| Reflection / Critic | งานที่ต้องการคุณภาพหรือความเสี่ยงสูง | ตรวจความครบถ้วนและข้อผิดพลาด | เพิ่ม latency และ Token |
| Tree / branch search | ทางเลือกหลายเส้นทาง งานเดิมพันสูง | เปรียบเทียบแนวทางได้ | ต้นทุนสูงมาก |
| Deterministic workflow + model | งานข้อมูล การเงิน Compliance | ลดความผิดพลาดจากการคาดเดา | ต้องลงทุนสร้าง scripts/schema |

งานง่ายและความถี่สูงควรใช้ reasoning depth ต่ำ; งานความเสี่ยงสูงหรือมีผลภายนอกควรเพิ่ม planning, verification และ human approval แทนการเพิ่ม “คิด” โดยไร้ขอบเขต[5][6]

## แยกการคิดออกจากการลงมือทำ

อย่าให้ model เปลี่ยนจาก “วิเคราะห์” ไป “ทำ action ที่มีผลจริง” โดยไม่มีชั้นควบคุม

```text
Model decision
   ↓
Structured decision object
   ↓
Schema validation
   ↓
Policy / permission check
   ↓
Approval gate, if needed
   ↓
Tool execution
   ↓
Validated observation returned to model
```

ตัวอย่าง decision object:

```json
{
  "next_step": "use_skill",
  "skill_name": "monthly-reporting",
  "goal": "Prepare a monthly KPI executive summary",
  "required_inputs": [
    "approved KPI dataset",
    "metric definitions"
  ],
  "tool_calls": [
    {
      "tool": "validate_report_data",
      "arguments": {
        "dataset_id": "monthly-kpi-2026-09"
      }
    }
  ],
  "success_criteria": [
    "All required KPI fields are present",
    "Metrics are traceable to approved data",
    "Output passes report validation"
  ],
  "requires_approval": false
}
```

Runtime ควรตรวจว่า Skill/tool มีอยู่จริง, argument ตรง schema, Agent มีสิทธิ์, scope อยู่ใน policy และ action ที่เป็น external write ได้รับ approval แล้วก่อน execute โครงสร้างนี้ทำให้ reasoning ระดับระบบตรวจสอบได้ แม้ internal reasoning ของโมเดลจะไม่ใช่สิ่งที่ควรพึ่งพาเป็นหลัก[2][7]

## Thinking สำหรับ Agent Skills

ในการใช้ Agent Skills ให้ใช้ Progressive Disclosure เพื่อให้ Agent คิดจาก context เท่าที่จำเป็น:

```text
1. อ่าน Skill catalog: name + description
2. จัดประเภท intent และเลือก candidate Skill
3. โหลด SKILL.md เฉพาะ Skill ที่ตรงที่สุด
4. อ่าน references เฉพาะเมื่อ workflow ระบุว่าใช้
5. รัน scripts สำหรับ calculation/validation ที่ deterministic
6. ใช้ assets เฉพาะตอนสร้าง deliverable
7. ตรวจผลลัพธ์ตาม quality gate ใน SKILL.md
```

ตัวอย่าง:

```text
คำขอ: “ช่วยทำสรุป KPI เดือนนี้ให้ผู้บริหาร”

Thinking flow:
1. ตรวจว่าเป็น reporting intent ไม่ใช่ dashboard design หรือ forecasting
2. เลือก Skill: monthly-reporting
3. โหลด SKILL.md
4. เปิด metric-definitions.md เพื่อยืนยันนิยาม KPI ที่พบ
5. รัน calculate_kpis.py แทนการคำนวณใน prompt
6. ใช้ executive-summary-template.md
7. รัน validate_report.py
8. สรุปเฉพาะตัวเลขที่ผ่าน validation พร้อมข้อจำกัด
```

การแยก workflow, documents และ deterministic scripts ทำให้ Agent ลดการคาดเดา ลด context ที่ไม่จำเป็น และประหยัด Token

## กติกาออกแบบ Thinking

### เป้าหมายต้องวัดผลได้

**ไม่ดี**

```text
ช่วยจัดการรายงานให้ดี
```

**ดีกว่า**

```text
สร้าง executive summary ไม่เกิน 5 bullets,
มี KPI actual/target/variance,
ระบุแหล่งข้อมูลและข้อจำกัด,
และผ่าน report validator
```

Agent ควรวางแผนจาก outcome และ acceptance criteria ไม่ใช่จากเป้าหมายกว้าง ๆ

### ให้ Tool ส่ง “ข้อมูลตัดสินใจ” กลับมา

Tool response ที่ดีไม่ควรคืน raw log ยาว ๆ แต่ควรคืนผลที่ Agent ใช้เลือก action ถัดไปได้ เช่น status, counts, errors, sample ที่ปกปิดข้อมูล และ next action ที่อนุญาต เครื่องมือที่มี schema/description ชัดและตอบกลับอย่าง token-efficient ช่วย Agent ใช้งานได้แม่นยำขึ้น[3]

```json
{
  "valid": false,
  "row_count": 12450,
  "missing_required_fields": ["target_value"],
  "invalid_rows": 17,
  "safe_examples": [
    {
      "row_id": "row-381",
      "issue": "target_value is null"
    }
  ],
  "next_allowed_actions": [
    "request corrected dataset",
    "produce partial report with limitation"
  ]
}
```

### จำกัดการวนลูป

กำหนด:

- `max_steps`
- `max_tool_calls`
- `max_retries_per_tool`
- timeout ต่อ tool และต่อ task
- token/cost budget
- stop condition
- escalation condition

ตัวอย่าง policy:

```text
- Retry transient tool errors ได้ไม่เกิน 2 ครั้ง
- ถ้า required data validation ไม่ผ่าน: หยุดการคำนวณและขอข้อมูลใหม่
- ถ้าเกิน 8 tool calls: สรุปสถานะและ escalate
- External write ทุกกรณีต้องรอ approval
```

โดยไม่มี budget และ stop condition Agent อาจวน retry หรือค้นข้อมูลต่อไปแม้ไม่มีโอกาสทำงานสำเร็จ

### วาง Verification เป็นส่วนหนึ่งของ Plan

อย่ารอให้ตรวจเฉพาะตอนท้าย ควรมี quality gate ระหว่างทาง:

```text
Validate input
   ↓
Compute / retrieve
   ↓
Validate intermediate result
   ↓
Generate output
   ↓
Validate output
   ↓
Approve / deliver
```

สำหรับงานที่มีความเสี่ยง ให้ deterministic validator มาก่อน LLM critic เพราะผลตรวจจาก schema/rule/script สามารถทำซ้ำและ audit ได้ดีกว่า[2][7]

## สิ่งที่ไม่ควรทำ

| Anti-pattern | ผลเสีย | วิธีที่ดีกว่า |
|---|---|---|
| ให้ Agent “คิดให้ละเอียด” โดยไม่กำหนด goal | ใช้ Token มากและยังหลุด scope | กำหนด success criteria และ step budget |
| ให้ Agent เลือก/เรียกทุก tool ได้ | tool misuse และ data exposure | ใช้ allowlist และ schema validation |
| ส่ง context ทั้งหมดทุก turn | ค่าใช้จ่ายสูงและ attention ลด | Progressive Disclosure + retrieval เฉพาะส่วน |
| ให้ model คำนวณหรือ validate ทุกอย่าง | ผลไม่ deterministic | ใช้ script / typed validator |
| ใช้ reflection ทุกงาน | เพิ่ม latency/cost โดยไม่จำเป็น | เปิด verifier เฉพาะงานที่ซับซ้อนหรือเสี่ยง |
| แสดง reasoning ยาวใน log หรือส่งให้ downstream ทุกครั้ง | เพิ่มข้อมูลอ่อนไหว/Token และทำให้ trace รก | เก็บ decision summary, evidence และ status ที่มีโครงสร้าง |
| ให้ action เกิดก่อน policy check | เสี่ยงต่อ write ผิดหรือข้อมูลรั่ว | validate → authorize → approve → execute |
| ไม่มี exit condition | loop ไม่จบและต้นทุนพุ่ง | จำกัด step, retry, timeout และ budget |

## Observability ที่ควรเก็บ

เพื่อ debug “Agent คิดผิดตรงไหน” ให้เก็บ trace ที่เป็น structured โดยไม่ต้องบันทึก reasoning ระดับละเอียด:

```text
task_id
session_id
agent/model version
input classification
selected skill and alternatives
plan version / decision summary
tool requested and sanitized arguments
policy and schema check result
tool outcome, latency, retry count
retrieved resource IDs
validation outcomes
approval status
final status: completed / blocked / failed / escalated
token usage and estimated cost
```

การ trace ระดับ plan, tool, retrieval และ validation ช่วยให้ดูได้ว่า failure อยู่ที่ routing, missing context, tool contract, permission, timeout หรือ synthesis โดยไม่ต้องพึ่งข้อความคิดภายในที่ยาวและไม่เสถียร[2]

## Blueprint แบบใช้งานจริง

```text
User request
    ↓
Classify + risk check
    ↓
Select Skill / workflow
    ↓
Create structured plan with success criteria
    ↓
For each step:
    validate state and inputs
    authorize tool
    execute tool/script
    validate observation
    update plan or stop
    ↓
Validate final output
    ↓
Require approval if external/destructive action
    ↓
Deliver answer + auditable summary
```

สรุป: Agent ที่ “คิดดี” ไม่ใช่ Agent ที่คิดยาวที่สุด แต่เป็น Agent ที่ **ตั้งเป้าหมายชัด, ใช้ context เท่าที่จำเป็น, เลือก tool ถูก, ตรวจผลทุกจุดสำคัญ, รู้เมื่อควรหยุดหรือขอความช่วยเหลือ, และไม่ทำ action เสี่ยงโดยไม่มี policy/approval**[1][2][3]

AGENTS API

**Agents API** คือ API สำหรับสร้าง Agent ที่ทำงานต่อเนื่องใน cloud โดยกำหนด model, instructions, tools, MCP servers และ sandbox environment ได้ ระบบจัดการ session, orchestration, context compaction และ recovery ให้ ขณะที่แอปของคุณกำหนดเครื่องมือและสภาพแวดล้อมการทำงานของ Agent[1][2]

## องค์ประกอบหลัก

| องค์ประกอบ | ความหมาย | ตัวอย่างการใช้ |
|---|---|---|
| **Agent** | นิยามความสามารถของ Agent: model, instructions, tools, MCP servers และ policy | Agent สำหรับวิเคราะห์รายงานหรือแก้ไขโค้ด |
| **Environment** | sandbox หรือ computer ที่ Agent ใช้เข้าถึงไฟล์ รันคำสั่ง โหลด Skills และสร้าง artifact | workspace ของ repository หรือเอกสารภายใน |
| **Session** | หน่วยงานที่ทำงานต่อเนื่อง เก็บ state ของงานหลาย turn | งาน refactor ที่ต้องทำหลายขั้นตอน |
| **Turn / Task** | คำสั่งหรือข้อความที่ส่งให้ Agent ทำงาน | “เพิ่ม routing eval ให้ Skill นี้” |
| **Events / Items** | เหตุการณ์และผลลัพธ์ระหว่าง execution | status, tool call, output, request for input |
| **Tools** | ความสามารถเชิง action เช่น shell, file edit, function, MCP, web search | รัน test, อ่าน schema, เรียก internal API |
| **Skills** | workflow/reusable instructions และไฟล์สนับสนุน | `evaluate-skill-routing`, `create-agent-skill` |
| **Guardrails / approvals** | ด่านตรวจ input/output หรือ human review ก่อน action เสี่ยง | ขออนุมัติก่อน deploy หรือส่งข้อมูลออกนอกองค์กร |

Agents API เหมาะกับงานที่ต้องมี state ต่อเนื่อง, ใช้ไฟล์และ sandbox, รันคำสั่ง, เชื่อม MCP, ทำงานยาว และต้องการติดตาม progress ผ่าน streaming หรือ webhooks[1][3]

## Agents API กับ SDK

| ทางเลือก | เหมาะเมื่อ | จุดเด่น |
|---|---|---|
| Agents API | ต้องการ managed cloud agent, durable session, orchestration และ sandbox ที่จัดการโดยผู้ให้บริการ | ลดภาระสร้าง agent loop, state และ recovery เอง |
| Agents SDK | ต้องการสร้าง agent app แบบ code-first และควบคุม execution/runtime มากขึ้น | รองรับ agent, tools, guardrails, handoffs และ sandbox agents |
| Responses API + Tools | ต้องการ workflow แบบ stateless หรือเรียก tool เป็นครั้ง ๆ | โครงสร้างเรียบง่าย ควบคุม request/response ตรงไปตรงมา |
| MCP server | ต้องการ expose ระบบหรือข้อมูลภายในเป็น tool มาตรฐานให้ Agent หลาย runtime ใช้ | แยก integration จาก agent workflow |

Agents SDK เป็นชุด primitives สำหรับสร้าง Agent โดยตรง เช่น Agents, sandbox agents, tools, handoffs และ guardrails ขณะที่ Agents API คือ managed runtime สำหรับ session และ orchestration ใน cloud[1][4][5]

## ใช้ Skills ผ่าน API

Skill เป็นไดเรกทอรีที่มี `SKILL.md` และไฟล์สนับสนุน Agent สามารถค้นพบ Skill จาก capability directory ภายใน sandbox ได้[6]

```text
workspace/
├── AGENTS.md
├── app/
├── capabilities/
│   └── skills/
│       ├── create-agent-skill/
│       │   ├── SKILL.md
│       │   ├── references/
│       │   └── assets/
│       └── evaluate-skill-routing/
│           ├── SKILL.md
│           ├── scripts/
│           └── references/
└── tests/
```

แนวคิดการตั้งค่า:

```json
{
  "environment": {
    "capability_directories": [
      "/workspace/capabilities/skills"
    ]
  }
}
```

เมื่อ runtime รู้จัก capability directory แล้ว Agent จะค้นหา Skill จาก subdirectory ที่มี `SKILL.md` และโหลดแบบ Progressive Disclosure: เริ่มจาก metadata เพื่อค้นหา, โหลด instruction เต็มเมื่อเลือก Skill, แล้วค่อยเปิด `references/`, `scripts/` หรือ `assets/` ตามงาน[2][3][6]

## รูปแบบ API เชิงแนวคิด

ตัวอย่างต่อไปนี้เป็น **conceptual request shape** เพื่ออธิบายองค์ประกอบ ไม่ควรคัดลอกไปเรียก production โดยไม่ตรวจ endpoint, SDK version และ schema ล่าสุดจากเอกสารของ provider

```json
{
  "agent": {
    "model": "<approved-model>",
    "instructions": "Follow AGENTS.md. Use a relevant Skill when available. Do not make external writes without approval.",
    "tools": [
      {
        "type": "shell",
        "environment": {
          "capability_directories": [
            "/workspace/capabilities/skills"
          ]
        }
      },
      {
        "type": "mcp",
        "server_label": "internal-knowledge"
      }
    ]
  },
  "environment": {
    "type": "sandbox",
    "workspace": "/workspace"
  },
  "task": {
    "input": "สร้าง Skill สำหรับตรวจสอบข้อมูลรายงานรายเดือน พร้อม trigger evals"
  }
}
```

ลำดับการทำงานทั่วไป:

1. สร้าง session และระบุ Agent, environment และ tools
2. รอ sandbox/environment พร้อมใช้งาน
3. ส่ง task หรือข้อความผู้ใช้เพื่อเริ่ม turn
4. ติดตาม events ผ่าน streaming หรือ webhook
5. Agent อ่าน context, เลือก Skill, เรียก tools และสร้าง output
6. แอปตอบ approval request หรือส่งข้อมูลเพิ่มเมื่อ Agent ต้องการ
7. ส่ง task ต่อใน session เดิมเมื่ออยากให้ Agent ทำงานต่อหรือแก้ไขงานเดิม[1]

## เลือกประเภท Tools

| Tool | ใช้กับงาน | ข้อควรควบคุม |
|---|---|---|
| Hosted tools | web search, file search, code interpreter, image generation | ตรวจ data egress และต้นทุน |
| Shell / sandbox | รัน script, test, formatter, build, แก้ไฟล์ | sandbox, workspace boundary, command allowlist |
| Function tool | งาน deterministic เช่น calculation, validation, transform, internal API wrapper | JSON Schema, input validation, timeout, audit log |
| MCP server | เชื่อม CRM, knowledge base, Git, database, ticketing | scoped credential, tool allowlist, approval gate |
| Agent as tool | ส่งต่องานไป specialist agent | กำหนด ownership และ output contract |
| Computer use | งานที่ต้องใช้ UI/browser | จำกัด domain, ยืนยันก่อน action ภายนอก |

SDK รองรับ hosted tools, function tools, MCP servers, execution tools และ sandbox capabilities; function tool เหมาะกับ action ที่ต้องเป็น deterministic เช่น lookup, calculation, file transformation หรือ validation[7][8]

## Security และ Governance

กำหนดควบคุมอย่างน้อย 5 ชั้น:

1. **Prompt/Skill layer** — กำหนด scope, ข้อห้าม, quality gates และ “ask before” ใน `AGENTS.md`/`SKILL.md`
2. **Tool layer** — ใช้ JSON Schema ตรวจ input, allowlist operation, timeout และการจัดการ error
3. **Credential layer** — ใช้ credential แบบ short-lived และจำกัด scope; ห้ามใส่ secrets ใน Skill, code หรือ eval fixture
4. **Runtime layer** — sandbox, filesystem boundary, network egress policy, CPU/time limit และ dependency allowlist
5. **Human approval layer** — บังคับอนุมัติก่อน external write, deploy, publish, destructive command หรือการส่งข้อมูล sensitive ออกนอกขอบเขต

อย่าถือว่า metadata เช่น `allowed-tools` ใน `SKILL.md` เป็นตัวบังคับสิทธิ์จริง เพราะการบังคับต้องทำที่ tool runtime, credential scope และ approval gate

## Checklist เริ่มใช้งาน

- กำหนด input/output contract ของ Agent ก่อนเขียน prompt
- เลือกว่าจะใช้ managed Agents API หรือ SDK แบบควบคุม runtime เอง
- เริ่มจาก tool น้อยที่สุดตามหลัก least privilege
- ใช้ Skills สำหรับ workflow ที่ซ้ำและต้องมีมาตรฐาน
- mount Skills ผ่าน capability directory ใน sandbox
- ใช้ function tools สำหรับงาน deterministic และตรวจ input ด้วย schema
- แยก read-only, local write และ external write tools
- วาง approval gate ก่อน action ที่ย้อนกลับยาก
- เก็บ trace, tool call, latency, error rate และ token/cost metrics
- สร้าง unit test, tool contract test, routing eval และ security regression test
- รัน eval ทุกครั้งที่เปลี่ยน `description`, routing, tools หรือ policy[1][6][7][8]

Weight ไม่ควรหมายถึง “ความสำคัญของไฟล์” อย่างเดียว แต่ควรหมายถึง ความมั่นใจ/ความเกี่ยวข้องของ relationship หรือ evidence

ดังนั้น Agent สามารถตัดสินใจว่าอะไรควรถูกโหลดก่อน

2. Weight คิดจากอะไร

ผมแนะนำให้ใช้หลายปัจจัย ไม่ใช้เลขเดียวแบบ hard-coded

weight =
    semantic_similarity
  + explicit_link
  + dependency_strength
  + freshness
  + authority
  + execution_relevance

เช่น normalize เป็น 0.0 → 1.0

Signal	ความหมาย

explicit_link	มี [[link]] โดยตรง
semantic_similarity	เนื้อหามีความหมายใกล้กัน
dependency_strength	dependency จริง
freshness	ข้อมูลยังใหม่
authority	source นี้เป็น canonical source หรือไม่
execution_relevance	เกี่ยวข้องกับ task ปัจจุบันแค่ไหน


ตัวอย่าง:

{
  "source": "Agent.md",
  "target": "Skill-SHA.md",
  "relation": "requires",
  "weight": 0.94,
  "evidence": [
    "explicit-link",
    "semantic-match",
    "task-relevance"
  ]
}
