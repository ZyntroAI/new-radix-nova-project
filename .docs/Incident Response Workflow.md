🚨 Incident Response Workflow — ขั้นตอนจัดการเหตุการณ์ความมั่นคง
 
"ไม่ใช่ว่าจะไม่เกิด แต่เมื่อเกิดขึ้น — เรารู้ว่าต้องทำอะไร เป็นขั้นตอน และไม่ต้องคิดในเวลาวิกฤต" ✅ IR Workflow = แผนปฏิบัติการฉุกเฉินที่ทุกคนในทีมต้องรู้และทำตามได้
 
 
 
📋 ภาพรวมกระบวนการ — 6 ขั้นตอนหลัก
 
plaintext
  
1. DETECTION   → ค้นพบและแจ้งเตือน
       ⬇️
2. TRIAGE      → ประเมินระดับความรุนแรง
       ⬇️
3. CONTAINMENT → จำกัดวง — หยุดความเสียหายก่อน
       ⬇️
4. INVESTIGATION → สืบสวน — เก็บหลักฐาน วิเคราะห์สาเหตุ
       ⬇️
5. ERADICATION & RECOVERY → กำจัดสาเหตุ → กู้คืนระบบ
       ⬇️
6. POST-MORTEM → บทเรียน → ปรับปรุง → ป้องกันไม่ให้เกิดซ้ำ
 
 
 
 
🔴 ระดับความรุนแรง — จัดลำดับความสำคัญ
 
ระดับ สี ความหมาย เวลาตอบสนอง ตัวอย่าง 
Critical 🔴 แดง ระบบหลักเสียหาย ข้อมูลสำคัญรั่ว ระดับองค์กร ทันที — ตลอด 24 ชม. ข้อมูลลูกค้ารั่ว, ระบบล็อกอินพัง, Ransomware 
High 🟠 ส้ม ส่วนสำคัญได้รับผลกระทบ ยังไม่กระทบทั้งระบบ ภายใน 1 ชม. สิทธิ์ผิดปกติ, พบช่องโหว่ในระบบภายใน 
Medium 🟡 เหลือง ปัญหาที่ต้องแก้ แต่ไม่กระทบการทำงานหลัก ภายใน 1 วัน Log หายบางส่วน, การแจ้งเตือนผิดพลาด 
Low 🟢 เขียว ข้อสงสัยหรือเหตุการณ์เล็กน้อย ภายใน 1 สัปดาห์ ล็อกอินผิดพลาดจากผู้ใช้ปกติ 
 
 
 
🔔 ขั้นที่ 1: Detection — ค้นพบและแจ้งเตือน
 
✅ ช่องทางการแจ้งเตือน
 
- 🤖 Automated Alerts: SIEM, Prometheus Alertmanager, Keycloak Events, WAF Logs
- 👤 User Report: แบบฟอร์ม/อีเมล/ช่องทางด่วน — ใครก็ตามแจ้งได้
- 🔍 Periodic Audit: ตรวจสอบ Log และรายงานเป็นประจำ
 
✅ เมื่อพบเหตุการณ์ — สิ่งที่ต้องบันทึกทันที
 
❌ ห้ามลบ/แก้ไขอะไรในระบบก่อน — บันทึกข้อมูลเบื้องต้นก่อนทุกอย่าง
 
plaintext
  
📝 บันทึกเบื้องต้น
• เวลาที่พบ: __________ เวลาที่เกิด: __________
• ผู้แจ้ง: __________ ช่องทาง: __________
• รายละเอียดเหตุการณ์: ________________________________
• ระบบที่ได้รับผลกระทบ: ________________________________
• หลักฐานเบื้องต้น (Screenshot/Log/Error): _____________
 
 
 
 
⚡ ขั้นที่ 2: Triage — ประเมินและตัดสินใจ
 
✅ คำถามเพื่อประเมินระดับ
 
1. ระบบอะไรได้รับผลกระทบ? — ระบบหลักหรือรอง?
2. ข้อมูลอะไรเสี่ยง? — ข้อมูลส่วนตัว, ข้อมูลลับ, หรือแค่สถิติ?
3. ใครมีส่วนเกี่ยวข้อง? — ภายใน, ภายนอก, หรือบุคคลทั่วไป?
4. ขอบเขตกว้างแค่ไหน? — เครื่องเดียว, ทั้งคลัสเตอร์, หรือทั้งองค์กร?
5. มีหลักฐานการโจมตีหรือไม่? — สุ่มหรือมีเป้าหมาย?
 
✅ การแจ้งคนที่เกี่ยวข้อง
 
ระดับ ทีมที่ต้องแจ้ง ช่องทาง 
Critical ผู้บริหาร + ทีมความมั่นคง + เจ้าของระบบ โทรศัพท์ + แจ้งในกลุ่มทันที 
High ทีมความมั่นคง + เจ้าของระบบ ช่องทางหลักของทีมภายใน 1 ชม. 
Medium เจ้าของระบบ ตามตารางงาน 
Low บันทึกในระบบติดตาม ตรวจสอบตามกำหนด 
 
📞 เบอร์ติดต่อฉุกเฉินต้องอยู่ที่หน้าแรกของแผนนี้ — ไม่ต้องค้นหาในเวลาจริง
 
 
 
🛡️ ขั้นที่ 3: Containment — จำกัดวงก่อนทุกอย่าง
 
เป้าหมาย: หยุดความเสียหายให้ได้เร็วที่สุด — ก่อนจะไปสืบสวน
 
✅ ทันทีที่ยืนยันเหตุการณ์:
 
การดำเนินการ เมื่อไหร่ วิธี 
🔒 เปลี่ยนรหัสผ่าน/เพิกถอน Token ที่เสี่ยง รั่วไหล/ถูกขโมย Keycloak → ยกเลิกเซสชัน + หมุน Client Secret 
🚫 บล็อก IP/บัญชีที่ไม่ถูกต้อง พฤติกรรมผิดปกติ WAF, Firewall, Keycloak → ปิดบัญชี 
🔌 แยกระบบที่เสียหายออกจากเครือข่าย แพร่กระจายได้ Disconnect NIC / Network Policy — ไม่ให้ติดต่อภายในอื่นได้ 
💾 เก็บ Snapshot ของระบบที่เกิดเหตุ ก่อนจะแก้ไขอะไร AWS AMI / Docker commit / PVC snapshot — สำหรับสืบสวน 
 
⚠️ ห้ามทำต่อไปนี้: ❌ รีบ Format เครื่อง, ❌ ลบ Log, ❌ ปิดระบบโดยไม่เก็บหลักฐาน, ❌ พยายามตรวจสอบเองโดยไม่บันทึก — ทุกอย่างต้องมีหลักฐาน
 
 
 
🔍 ขั้นที่ 4: Investigation — สืบสวนและวิเคราะห์
 
✅ เก็บหลักฐานตามลำดับความสำคัญ
 
ความผันผวนสูง → ต่ำ: หายไปก่อน → เก็บก่อน
 
ลำดับ สิ่งที่เก็บ วิธี หมายเหตุ 
1️⃣ 📡 หน่วยความจำ/กระบวนการ  ps aux ,  netstat , memory dump หายเมื่อรีสตาร์ท 
2️⃣ 📋 Log ระบบและแอปพลิเคชัน  /var/log/ , container logs, Keycloak events อาจถูกลบทับ 
3️⃣ 💾 ไฟล์และระบบไฟล์  ls -la ,  stat , rsync คงที่กว่าแต่อาจถูกแก้ไข 
4️⃣ 🌐 ทราฟฟิกเครือข่าย PCAP / Flow Logs บันทึกก่อนหน้า 
5️⃣ 📸 Snapshot ภาพรวม Backup หรือ Snapshot เก็บไว้เป็นหลักฐานถาวร 
 
✅ คำถามที่ต้องหาคำตอบ
 
- ❓ เกิดขึ้นได้อย่างไร? — จุดเริ่มต้นที่ไหน
- ❓ ใครทำ? — ภายใน, ภายนอก, หรือบุคคลทั่วไป
- ❓ เข้าถึงอะไรบ้าง? — ข้อมูลอะไรถูกอ่าน/แก้ไข/ลบ
- ❓ มีอยู่นานแค่ไหนแล้ว? — ตั้งแต่เมื่อไหร่ที่เริ่ม
- ❓ มีหลักฐานว่าถูกนำไปใช้ประโยชน์หรือไม่? — ข้อมูลอยู่ที่ไหน

🔧 ขั้นที่ 5: Eradication & Recovery — กำจัดและกู้คืน
 
✅ กำจัดสาเหตุ
 
- 🩹 ปิดช่องโหว่ / อัปเดตแพตช์
- 🔑 หมุนรหัสผ่าน/Token/Certificate ทั้งหมดที่เกี่ยวข้อง
- 🧹 ลบสคริปต์/แบ็คดอร์ที่แทรกซ้อน
- 📋 ตรวจสอบระบบอื่นๆ ที่อาจได้รับผลกระทบเช่นเดียวกัน
 
✅ กู้คืนระบบ
 
plaintext
  
ขั้นตอนการกู้คืน:
1. ✅ ตรวจสอบว่าสาเหตุถูกกำจัดแล้ว — ไม่ใช่แค่ซ่อนอาการ
2. ✅ กู้คืนจาก Backup ที่สะอาดและเชื่อถือได้
3. ✅ ติดตั้งแพตช์และการป้องกันก่อนเปิดระบบ
4. ✅ ทดสอบการทำงานและความปลอดภัย
5. ✅ เปิดระบบแบบค่อยเป็นค่อยไป — สังเกตอาการอย่างใกล้ชิด
6. ✅ แจ้งผู้ใช้งานตามช่องทางที่เหมาะสม
 
 
⚠️ Backup ต้องได้รับการตรวจสอบความสะอาดก่อนใช้ — ไม่กู้คืนสิ่งที่ติดมัลแวร์มาแล้ว
 
 
 
📝 ขั้นที่ 6: Post-Mortem — บทเรียนเพื่อป้องกันอนาคต
 
สำคัญที่สุด: ไม่ใช่เพื่อตำหนิคน แต่เพื่อเรียนรู้และป้องกันไม่ให้เกิดซ้ำ ✅

✅ หลักการ Post-Mortem ที่ดี
 
- ✅ Blame-free: ไม่ตำหนิบุคคล — วิเคราะห์กระบวนการและระบบ
- ✅ Root Cause: ขุดให้เจอสาเหตุที่แท้จริง ไม่ใช่แค่อาการ
- ✅ Actionable: ต้องมีงานที่ทำได้จริง พร้อมกำหนดเวลาและผู้รับผิดชอบ
- ✅ Share: แบ่งปันให้ทีมที่เกี่ยวข้องเรียนรู้ร่วมกัน
 
 
 
📑 ตัวอย่างสถานการณ์และการจัดการ
 
📌 สถานการณ์: พบ Token CI ถูก Commit เข้า Repository สาธารณะ
 
ขั้นตอน การดำเนินการ เวลาเป้าหมาย 
Detection สัญญาณเตือนจากเครื่องมือสแกน — พบ Credential ใน Git ทันที 
Triage 🟡 High — Token มีสิทธิ์เขียนแคช ภายใน 15 นาที 
Containment เพิกถอน Token ทันทีใน Keycloak → ปิดบัญชีชั่วคราว ภายใน 30 นาที 
Investigation ตรวจสอบ Log — มีการใช้ Token จาก IP แปลกหรือไม่? ภายใน 2 ชม. 
Eradication ลบประวัติ Git — หมุน Token ใหม่ — สแกนประวัติทั้งหมด ภายใน 1 วัน 
Post-Mortem เปิดใช้ GitGuardian — ปรับกฎ Commit — ฝึกอบรมทีม ภายใน 1 สัปดาห์
