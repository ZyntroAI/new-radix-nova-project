How do I invoke functions with curl using a JWT

Send the user’s **JWT** in the `Authorization: Bearer` header. Put your Supabase publishable key in the separate `apikey` header—not in the bearer token field.[1]

## 1. Invoke a local function

Start the function with JWT verification enabled—omit the `--no-verify-jwt` flag used in the earlier diagnostic example:

```bash
supabase functions serve check-secrets \
  --env-file .env.local
```

Then invoke it using an access token issued by your local Supabase Auth instance:

```bash
export SUPABASE_URL="http://127.0.0.1:54321"
export SUPABASE_API_KEY="YOUR_LOCAL_PUBLISHABLE_OR_ANON_KEY"
export ACCESS_TOKEN="YOUR_LOCAL_USER_ACCESS_TOKEN"

curl -i \
  "$SUPABASE_URL/functions/v1/check-secrets" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "apikey: $SUPABASE_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"test":true}'
```

The bearer token must belong to the same Supabase environment as the endpoint. A token signed with another project’s key fails JWT verification.[1]

## 2. Get a user access token with curl

For an existing email/password user, sign in through Supabase Auth. This example uses `jq` to construct the JSON and extract the token:

```bash
export TEST_EMAIL="test@example.com"
read -r -s -p "Test user password: " TEST_PASSWORD
printf '\n'

AUTH_RESPONSE=$(curl --silent --show-error --fail-with-body \
  "$SUPABASE_URL/auth/v1/token?grant_type=password" \
  -H "apikey: $SUPABASE_API_KEY" \
  -H "Content-Type: application/json" \
  --data "$(jq -n \
    --arg email "$TEST_EMAIL" \
    --arg password "$TEST_PASSWORD" \
    '{email: $email, password: $password}')") || exit 1

export ACCESS_TOKEN
ACCESS_TOKEN=$(printf '%s' "$AUTH_RESPONSE" |
  jq -er '.access_token') || exit 1

unset TEST_PASSWORD AUTH_RESPONSE
```

Use the session’s access token, not its refresh token. Supabase user access tokens are supplied to API requests through `Authorization: Bearer <jwt>`.[2]

## 3. Invoke a production function

Use the production URL, production publishable key, and a user token issued by production Auth:

```bash
export SUPABASE_URL="https://YOUR_PROJECT_REF.supabase.co"
export SUPABASE_API_KEY="YOUR_PRODUCTION_PUBLISHABLE_KEY"
export ACCESS_TOKEN="YOUR_PRODUCTION_USER_ACCESS_TOKEN"

curl -i \
  "$SUPABASE_URL/functions/v1/create-order" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "apikey: $SUPABASE_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{
    "productId": "product-123",
    "quantity": 2
  }'
```

Publishable keys such as `sb_publishable_...` are not JWTs. Do not use `Authorization: Bearer sb_publishable_...`; reserve that header for the user token.[1]

## 4. Keep verification enabled

In your existing `supabase/config.toml`, check that the function is not configured to bypass JWT verification:

```toml
[functions.create-order]
verify_jwt = true

[functions.check-secrets]
verify_jwt = true
```

With verification enabled, the platform rejects missing, malformed, or invalid JWTs before your handler executes. Your handler must still enforce application-specific permissions; a valid token does not mean the user may access every order.[1]

## Troubleshooting

| Symptom | What to check |
|---|---|
| `401 Unauthorized` before the handler runs | Missing, expired, invalid, or wrong-project JWT |
| Bearer value begins with `sb_publishable_` or `sb_secret_` | Move it to `apikey`; use a user access token in `Authorization` |
| Local invocation accepts no token | Remove `--no-verify-jwt` and check the function’s `verify_jwt` setting |
| Request reaches your handler but returns `500` | Inspect local logs; for `check-secrets`, confirm `.env.local` contains the required variables |

The platform JWT check and the function’s own logic are separate: first establish who is calling, then validate what they are allowed to do.[1]
