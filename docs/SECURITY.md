3. แนวทางปฏิบัติที่ดีสำหรับนักพัฒนา
 
✅ ก่อนส่งโค้ด
 
ตรวจสอบให้แน่ใจว่า ไม่มี API Key, Password หรือ Token อยู่ในโค้ด
ใช้ไฟล์  .env.local  สำหรับค่าที่เป็นความลับ — อย่า Commit ขึ้น Git
ตรวจสอบ  .gitignore  ให้ถูกต้อง
รัน  npm run lint  และ  npm run typecheck  ก่อน Push
ตรวจสอบโค้ดด้วยตาเองก่อนส่ง Pull Request
 
✅ การเขียนโค้ดที่ปลอดภัย
 
typescript  
// ✅ ใช้ Environment Variable แทน Hard-coded Secret
const apiKey = process.env.OPENAI_API_KEY;

// ✅ ตรวจสอบข้อมูลนำเข้าก่อนใช้งาน
if (typeof userInput === 'string' && userInput.length < 500) {
  // ประมวลผลข้อมูล
}

// ✅ ใช้ TypeScript เพื่อลดความผิดพลาด
interface RequestBody {
  message: string;
  userId?: string;
}
 
 
❌ สิ่งที่ห้ามทำ
 
- ❌ ห้าม Commit ความลับขึ้น Repository สาธารณะหรือส่วนตัว
- ❌ ห้ามฝัง API Key ฝั่ง Client-Side (ใช้  NEXT_PUBLIC_  เฉพาะข้อมูลสาธารณะเท่านั้น)
- ❌ ห้ามปิดการใช้งาน Linter หรือ Type Check โดยไม่มีเหตุผลอันสมควร
- ❌ ห้ามรับข้อมูลจากผู้ใช้โดยไม่ตรวจสอบและทำความสะอาดข้อมูล
- ❌ ห้ามใช้โทเค็นเดียวกันระหว่างสภาพแวดล้อม Development และ Production
 
 
 
4. การจัดการความลับและ API Key
 
4.1 หลักการสำคัญ
 
ประเภทข้อมูล วิธีจัดเก็บ ต้องไม่เผยแพร่ 
API Keys (OpenAI, Anthropic)  .env.local , Vercel Env ✅ ทุกที่ ยกเว้นสภาพแวดล้อมรันไทม์ 
Database Credentials  .env.local , Secrets Manager ✅ ทุกกรณี 
JWT Secrets / Signing Keys Environment Variable เท่านั้น ✅ ทุกกรณี 
ข้อมูลสาธารณะ (URL, Config)  NEXT_PUBLIC_*  หรือในโค้ดได้ ✅ ปลอดภัย 
 
4.2 หากเผลอทำหาย / รั่วไหล
 
1. หมุนเปลี่ยน API Key ทันที ที่หน้า Dashboard ของผู้ให้บริการ
2. เพิกถอน Token หรือ Credential เดิม
3. ตรวจสอบ Log และการใช้งานที่ผิดปกติ
4. แจ้งผู้ดูแลระบบ
5. ตรวจสอบประวัติ Commit และทำความสะอาดหากจำเป็น
 
💡 คำสั่งสำหรับลบไฟล์ที่มีความลับออกจาก Git History:
 
bash  
# คำเตือน: ใช้ด้วยความระมัดระวัง
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env.local" \
  --prune-empty --tag-name-filter cat -- --all
 
 
 
 
5. การรายงานช่องโหว่ความปลอดภัย
 
พบช่องโหว่หรือจุดอ่อนด้านความปลอดภัย? โปรดแจ้งเราทันที — เราจะจัดการอย่างเร่งด่วน
 
📧 ช่องทางติดต่อ
 
- อีเมล: security@zyntroai.com
- หัวข้ออีเมล: [Security Report] — รายงานช่องโหว่ใน new-radix-nova-project
- เวลาตอบกลับ: ภายใน 48 ชั่วโมง
- เวลาแก้ไข: ขึ้นอยู่กับความรุนแรง (วิกฤต: ภายใน 72 ชม.)
 
📝 ข้อมูลที่ควรระบุ
 
- ชื่อ/ส่วนของระบบที่พบปัญหา
- คำอธิบายและขั้นตอนการทำให้เกิดปัญหา
- ผลกระทบที่อาจเกิดขึ้น
- คำแนะนำวิธีแก้ไข (ถ้ามี)
- ข้อมูลสำหรับติดต่อกลับ
 
⚠️ ขอความกรุณา
 
- ❌ อย่าเปิดเผยปัญหาสู่สาธารณะ จนกว่าเราจะได้แก้ไขและเผยแพร่การแก้ไขแล้ว
- ✅ เรายินดีขอบคุณและอ้างอิงชื่อผู้ค้นพบในรายงานความปลอดภัย
 
 
 
6. นโยบายการเปิดเผยข้อมูล
 
- ระยะเวลา: เราจะเผยแพร่รายงานปัญหาความปลอดภัยหลังจากมีการแก้ไขแล้ว อย่างน้อย 7 วัน เพื่อให้ผู้ใช้มีเวลาอัปเดต
- ขอบคุณผู้ค้นพบ: เราจะระบุชื่อผู้รายงานในหน้า Credits เว้นแต่ผู้รายงานขอไม่ระบุชื่อ
- ข้อมูลที่เปิดเผย: ประเภทปัญหา, ผลกระทบ, เวอร์ชันที่ได้รับการแก้ไข และวิธีแก้ไข
 
 
 
7. การอัปเดตและแพตช์ความปลอดภัย
 
📦 การอัปเดต Dependencies
 
- ตรวจสอบช่องโหว่ของแพ็กเกจเป็นประจำ:
bash  
pnpm audit
# หรือ
npm audit
 
- Dependabot ถูกตั้งค่าในระบบแล้ว — จะแจ้งเตือนและสร้าง PR เมื่อพบช่องโหว่
- อัปเดตแพตช์ความปลอดภัยทันทีที่มีแจ้งเตือน — ไม่ควรปล่อยทิ้งไว้
 
🚀 กระบวนการเผยแพร่แพตช์
 
1. ยืนยันความรุนแรงและผลกระทบ
2. เตรียมการแก้ไขในสาขาแยก
3. ทดสอบความถูกต้อง
4. ออก Release พร้อมบันทึกการเปลี่ยนแปลงที่ชัดเจน
5. แจ้งเตือนผู้ใช้ให้อัปเดต
 
 
 
8. การตรวจสอบความปลอดภัยในกระบวนการพัฒนา
 
🔄 CI/CD — การตรวจสอบอัตโนมัติ
 
GitHub Actions จะรันการตรวจสอบทุกครั้งที่ Push โค้ด:
 
- CodeQL Analysis — ตรวจหาช่องโหว่ในโค้ด
- Dependency Scan — ตรวจสอบแพ็กเกจที่มีช่องโหว่ที่ทราบแล้ว
- Type Check & Lint — ลดความผิดพลาดที่อาจเป็นจุดอ่อน
 
🔐 การเข้าถึง Repository
 
- เฉพาะผู้มีส่วนร่วมที่ได้รับอนุญาตเท่านั้นที่สามารถ Push โค้ดได้
- Pull Request ต้องผ่านการตรวจสอบจากผู้ดูแลก่อนจึงจะรวมได้
- บันทึกการเปลี่ยนแปลงทั้งหมดจะถูกเก็บไว้ในประวัติ Git
 
 
 
📌 สรุปหลักการสำคัญ
 
หลักการ ความหมาย 
ลึกน้อยที่สุด ให้สิทธิ์เท่าที่จำเป็นเท่านั้น 
ไม่เชื่อข้อมูลนำเข้า ตรวจสอบและทำความสะอาดข้อมูลจากภายนอกเสมอ 
ความลับไม่อยู่ในโค้ด เก็บใน Environment Variable หรือ Secret Manager เท่านั้น 
รู้เท่าทันภัย ตรวจสอบและอัปเดตอย่างสม่ำเสมอ 
เปิดเผยอย่างรับผิดชอบ แจ้งก่อน — แก้ไขเสร็จแล้วค่อยเปิดเผย
