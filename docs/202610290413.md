How do I pass a service role key instead

If you mean the legacy Supabase **`service_role`** key—the JWT-shaped value starting with `eyJ...`—pass it as a bearer token instead of the user’s access token. Legacy `service_role` keys are JWTs; newer `sb_secret_...` keys are not and use a different pattern.[1][2]

## Invoke with a legacy service-role key

Run this only from a trusted terminal, backend, or CI environment:

```bash
export SUPABASE_URL="https://YOUR_PROJECT_REF.supabase.co"

# Read the key without displaying it or including its literal value in history.
read -r -s -p "Service-role key: " SERVICE_ROLE_KEY
printf '\n'

curl -i \
  "$SUPABASE_URL/functions/v1/create-order" \
  -H "Authorization: Bearer $SERVICE_ROLE_KEY" \
  -H "apikey: $SERVICE_ROLE_KEY" \
  -H "Content-Type: application/json" \
  --data '{
    "productId": "product-123",
    "quantity": 2
  }'

unset SERVICE_ROLE_KEY
```

Both headers use the same project’s legacy service-role key: `Authorization` supplies the JWT, and `apikey` supplies the project API credential. For local testing, use your local service-role key and `http://127.0.0.1:54321`, not production credentials.[1]

## Important: a valid JWT is not an admin permission check

The platform’s JWT verification establishes token validity; it does not make your endpoint service-role-only. If an endpoint is intended for administrative calls, your handler must explicitly enforce the required authorization rather than accepting every valid user token.[2]

Also, sending a service-role key to the function does not automatically change every database client inside it. Database privileges depend on the credentials and authorization context used to construct that client. Supabase’s service-role database credential bypasses Row Level Security, so keep it strictly server-side.[3]

## If your key starts with `sb_secret_...`

Use the `apikey` header instead:

```bash
curl -i \
  "$SUPABASE_URL/functions/v1/admin-task" \
  -H "apikey: $SUPABASE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  --data '{"action":"reconcile"}'
```

For this service-to-service pattern, configure the function’s authentication to validate the secret API key. Supabase recommends disabling `verify_jwt` for API-key-authenticated service calls and implementing the corresponding handler-level authentication; disabling JWT verification alone does not secure the endpoint.[2]

```toml
[functions.admin-task]
verify_jwt = false
```

Never put either privileged key in browser code, mobile applications, public repositories, or logs. Prefer newer secret keys for new service integrations; Supabase retains legacy service-role JWTs for backward compatibility.[1][3]
